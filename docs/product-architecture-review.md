# 智研產品與架構檢查（2026-09-27）

## 結論

智研的核心方向正確：把主張、證據、引用與交付決策留在同一條可稽核流程。現階段最大的風險不是功能不足，而是研究模組、歷史文件與使用者介面同時擴張，讓「降低法律錯誤」這個目的被工程名詞蓋住。

本輪採取的收斂原則是：**一條主要回答流程、一份正式資料模型、必要時才啟用進階研究功能。**

## 應保留的核心

1. `ExecutionContext` 作為單一執行狀態，集中保存事實、主張、證據、引用與閘門結果。
2. Claim → Evidence → Citation 的關聯，讓來源不是回答後才補上的裝飾。
3. DELIVER／ASK／HUMAN_REVIEW／STOP 等交付決策，讓系統可以承認資料不足。
4. 台灣法規與判決來源定位，以及後續人工覆核能力。
5. Qdrant 用於檢索、SQLite 用於原文與版本管理；不另建平行資料主線。

## 發現與處理

| 嚴重度 | 發現 | 影響 | 本輪處理 |
| --- | --- | --- | --- |
| 高 | `sub_agent.py` 多個同名函式重複定義 | Python 靜默覆寫前一版，錯誤難被看見 | 移除重複定義並新增 AST 防回歸測試 |
| 高 | 完整分析重複執行相同三法域研究 | 增加模型／工具費用，結果可能互相矛盾 | 改為一次研究、相容地重用結果 |
| 中 | 空法域清單未依文件回復預設值 | 可能送出零個研究任務 | 統一 `None` 與空清單行為 |
| 高 | 首頁充滿層級、模型與 token 等工程資訊 | 一般人不知道產品能幫什麼 | 改成「看得懂、查得到、不硬猜」 |
| 高 | 前端未呈現回答契約中的引用資料 | 使用者無法核對回答 | 新增引用區塊；判決整合分支回傳資料後即可呈現 |
| 中 | 文件首頁有重複表格與互相矛盾的模組數量 | 降低可信度並增加維護成本 | 改成單一使用者入口，技術細節下移 |

## 不應繼續擴張的地方

- 不再增加新的「層」、人格或平行 orchestration，除非有明確失敗案例與測試證明必要。
- 不把多代理或多模型設為一般問題的預設路徑；它們是高風險研究的選用功能。
- 不再建立第二套 Claim、Evidence、Citation 或交付決策型別。
- 不用 CI 綠燈、索引筆數或模型共識宣稱法律答案正確。
- 不在首頁展示內部模型、token、縮寫與版本層級；這些資訊留在維運與稽核介面。

## 後續停止目標

達成以下條件後，應停止新增架構，轉為真實案例驗收與錯誤修正：

1. 一般使用者可輸入事實，取得白話回答與可核對來源。
2. 缺資料、無來源、模型失敗與高風險問題都有可理解的明確結果。
3. 20–50 筆真實判決在持久環境完成同步、搜尋、重啟與備份還原驗收。
4. 主要流程沒有重複資料模型或重複外部呼叫。
5. 首頁、README 與實際產品能力一致，不宣稱尚未驗收的效果。
